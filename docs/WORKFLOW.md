# Workflow por hito con spec-kit

Cada hito de `ROADMAP.md` se implementa con una pasada del workflow `hito` de spec-kit (`.specify/workflows/hito/workflow.yml`). La persona está en los dos extremos y en ningún punto intermedio (ADR 0018): **escribe la entrada** —la sección del hito en `docs/ROADMAP.md`— y **lee el informe final**, que llega como cuerpo de la propuesta de cambio. Entre medias, los comandos `speckit.*` corren en modo headless (`claude -p`), los gates los deciden scripts y jueces con rúbrica, y el run solo se detiene por una causa mayor que detecta el código.

## Piezas

| Pieza | Dónde | Para qué |
|---|---|---|
| Constitución | `.specify/memory/constitution.md` | Principios, restricciones, DoD, las tres capas de gate y el criterio con el que se decide sin persona |
| Workflow | `.specify/workflows/hito/workflow.yml` | Secuencia, rondas de juez, bucle de tareas, revisión, cierre e informe |
| Pasos shell | `scripts/workflow/*.sh` | La lógica determinista de cada paso: prechecks, rondas, guardián, verificación, cuarentena, aceptación congelada, grabación, cierre e informe |
| Lanzador y supervisor | `scripts/hito.sh` | Comprueba `main` limpio, las credenciales y el entorno (ninguna credencial de Claude heredable, ningún directorio adicional), toma el candado de sesión única, impide el reposo del Mac y supervisa el run: espera ante límites de uso, reanuda fallos transitorios y solo se detiene ante una causa mayor o el rechazo de entrada |
| Sesión única | `scripts/workflow/sesion-unica.sh` + gancho `PreToolUse` en `.claude/settings.json` | Mientras vive un run, ninguna otra sesión de Claude Code puede editar ni cambiar el historial de ese árbol |
| Wrapper de modelo | `scripts/claude-modelo.sh` | Ejecutable de Claude para spec-kit: traduce `--model <modelo>@<esfuerzo>` a `--model` + `--effort`, y abre cada sesión de un paso dentro del sandbox de Claude Code (sin más red que la de las herramientas de Go, sin escribir fuera del repositorio y del temporal, sin leer los directorios con secretos), sin segundo plano, sin `claude` en su `PATH` y sin `.claude/settings.local.json` |
| Política de las sesiones | `scripts/workflow/politica-paso.sh` (por el mismo gancho `PreToolUse`) + `scripts/workflow/sin-modelo/claude` | Lo que una sesión de un paso no hace: leer credenciales, abrir sesiones con modelo, dejar nada en segundo plano ni escribir fuera del repositorio y del directorio temporal (ADR 0032) |
| Coste por paso | `scripts/coste-run.sh` | Consumo y coste estimado de un run por paso y por rol, desde los transcripts |
| Extensión git | `.specify/extensions/git/` | Rama `NNN-hN-slug` por hito |
| Skills | `.claude/skills/speckit-*` | Los comandos `/speckit-*` (generados por `specify init`, no editar a mano) |
| Artefactos | `specs/NNN-hN-slug/` | `spec.md`, `plan.md`, `research.md`, `tasks.md`, `checklists/`, `aceptacion/`, `gates/` |
| Evidencia de datos | `evidencias/<hito>/` | Material de origen grabado por `grabar_datos`, con `manifiesto.json` de huellas |

## Secuencia

```
extraer_hito (la sección del hito: la entrada de la persona)
→ specify → clarify_preguntas → ronda_clarify ×3 [resolver_clarify (proceso nuevo) → check_clarify] → completar_clarify → clarify_integrar
→ ronda_spec ×4 [cambios_spec → precheck_spec → juez_spec (juez de entrada) → leer_gate_spec → corrector_spec] → check_gate_spec   ← único rechazo posible antes del final
→ plan → ronda_plan ×4 [cambios → precheck → juez → leer → corrector] → check_gate_plan → commit
→ tasks → analyze → ronda_tasks ×4 [cambios → precheck → juez → leer → corrector] → check_gate_tasks → commit
→ bucle_tareas:
     siguiente_tarea (primera "- [ ] Tnnn" fuera de cuarentena; si no queda ninguna, converge una vez)
     → implementar_tarea (intento 1: modelo_implementacion; 2 y 3: modelo_escalada con el diagnóstico del anterior)
     → verificar (guardián de diff + «rojo primero» si [aceptacion] + manifiesto grabable si [datos] + make ci)
     → si rojo: redelimitada → reintento | reparar → verificar_reparacion → si sigue rojo, el diagnóstico va a la nota de la tarea
     → estado_cierre → commit_tarea → congelar_aceptacion ([aceptacion]) → grabar_datos ([datos] con manifiesto)
     (tras tres intentos sin verde: cuarentena y sigue)
→ activar_aceptacion (la suite congelada entra en make ci)
→ ci (make ci del hito) → si rojo: bucle_reparacion ×3 [reparar_hito → cerrar_reparacion]
→ barrido (artefactos y documentación contra el producto) → cerrar_barrido
→ iniciar_revision → iniciar_cierre
→ bucle_final ×3 (revisión final y cierre en un solo bucle, ADR 0030):
     pendiente_revision (¿algo fuera de gates/ que ningún juez ha visto? la 1.ª vuelta, el hito entero)
     → si lo hay: ronda_revision ×4 por ciclo [preparar_jueces (rango desde el último veredicto) → juez A ∥ juez B
                   → leer_revision → corrector_revision → cerrar_correccion] → cerrar_revision
     → publicar (push + propuesta de cambio) → medir_cierre (CI + evals sobre la cabeza)
     → si rojo y queda medición: reparar_cierre → cerrar_cierre (y la vuelta siguiente lo juzga antes de medir)
→ informe_final (cuerpo de la propuesta de cambio)
```

La fusión a `main` (squash-merge) y el release los decide siempre una persona; en una sesión interactiva, a petición suya, los ejecuta el agente con confirmación de cada orden (ADR 0020). El workflow deja la rama del hito commiteada, la empuja a `origin`, abre la propuesta de cambio y pone el informe como cuerpo. Nunca hace `merge`, ni push a `main`, ni push forzado, ni etiqueta: lo impiden los permisos de `.claude/settings.json` (fusionar y empujar una etiqueta son `ask`, que en headless no se ejecuta; push a `main`, forzado y borrados, `deny`) y, en el servidor, la protección de `main` en GitHub (`ci` y `snapshot` en verde, sin push forzado ni borrado). Sin gancho `pre-push` (ADR 0021). Motivación en `docs/ADR/0007-workflow-desatendido.md` y `docs/ADR/0018-workflow-autonomo-persona-en-los-extremos.md`.

## Qué detiene el run

Nada que decida un modelo. Solo esto:

| Parada | Quién la detecta | Qué deja |
|---|---|---|
| Rechazo de entrada | `check_gate_spec`: el juez de entrada lista motivos en `entrada` con tipo `contradiccion`, `sin_criterio_comprobable` u `objetivo_vacio` | `gates/informe-rechazo.md`: fragmento, por qué impide derivar un test y una pregunta cerrada por motivo. Se corrige la sección del hito y se relanza desde `main` |
| DAG bloqueado | `siguiente_tarea`: tres tareas seguidas en cuarentena sin ninguna en verde entre medias | `gates/dossier.md` |
| Dependencia externa inaccesible | `grabar_datos` (la fuente no responde tras un reintento), `publicar` o `medir_cierre` (push, `gh` o comprobaciones que no terminan en 3 h) | `gates/dossier.md` |
| Credencial ausente | `hito.sh` al arrancar (`claude`, `gh auth status`, `origin`) y el cierre | mensaje del supervisor o `gates/dossier.md` |
| Presupuesto de tiempo | `hito.sh`: el run supera `KITLEGAL_TIEMPO_MAXIMO` segundos (48 h) desde su primer paso | mensaje del supervisor |

Todo lo demás sigue: un gate que agota sus rondas pasa con sus motivos a `gates/<fase>-pendiente.md` (también un ciclo de la revisión final que juzga una reparación del cierre); una tarea que no sale entra en cuarentena; un corrector que toca lo que no debe se aparta; un cierre que sigue en rojo tras tres mediciones queda así en el informe. Juzgar lo que cambia el cierre no añade ninguna parada: si se agotan rondas o mediciones, los motivos van al informe, nunca en silencio.

## Tres capas de gate

Sigue la sección «Gates» de la constitución: cada comprobación vive en la capa más baja que pueda verificarla.

1. **Mecánica (shell, sin LLM).** `scripts/workflow/precheck.sh` corre antes de cada juez de artefactos y escribe sus defectos en `gates/<fase>-precheck.txt`: marcadores pendientes, checklists, «Fuera de alcance», ids de requisito únicos y citados, escenarios Dado/Cuando/Entonces, «Aceptación e2e» en el plan, la sección «Controles de umbral» del plan (que exista, que cada fila nombre requisitos que el spec define y que diga dónde vive su control), formato e ids de tareas, rutas declaradas, `[datos]`, una sola `[aceptacion]` y la primera, y ninguna tarea de plataforma, de persona ni con `KITLEGAL_RECORD`. **No paran el run**: `gate.sh leer` fuerza el rechazo mientras quede alguno y el corrector los arregla. `verificar.sh` ejecuta el guardián de diff y `make ci`, que encadena lint, `-race`, schema-check, drift de `references/`, test de arquitectura y golden files de citas.
2. **Juez LLM con rúbrica.** `juez_spec`, `juez_plan`, `juez_tasks` y los dos jueces finales reciben criterios fijos y escriben `{"veredicto","criterios":[{id,criterio,cumple,evidencia}],"motivos","observaciones"}` (el de entrada, además, `"entrada":[…]`). **No corrigen nada.** Revisan de forma exhaustiva dentro del umbral y, en rondas posteriores, comprueban primero los motivos anteriores. Si rechazan, un corrector (proceso distinto) aplica los motivos generalizando cada uno a su clase de defecto dentro del umbral de materialidad, y se vuelve a juzgar: hasta cuatro veredictos y tres correcciones. Un veredicto ausente o mal formado repite la ronda con un juez nuevo. Un motivo de alcance, frontera humana, privacidad, TOS, anomalías o decisión cerrada lo aplica el corrector con la lectura conservadora y deja una línea en `gates/supuestos.md`. Los autores (`specify`, `plan`, `tasks`) comprueban su artefacto contra la rúbrica y el precheck antes de entregar.

   Cinco reglas de la constitución («Gates», ADR 0028 y 0029) deciden qué es un motivo. Las cuatro primeras nacen de H7, donde spec y plan agotaron sus cuatro rondas con motivos sobre estados que el producto no alcanza, y donde un defecto de uso de `graph check` pasó por los cinco jueces; la de umbrales, de H7.2, cuyo 5 % de respuestas con expresiones prohibidas se medía en el cierre y solo se publicaba (10 de 51, y todo en verde):
   - **Umbral de materialidad** (todos los jueces; los correctores y `resolver_clarify` lo respetan): una ambigüedad, un hueco o un estado es defecto solo si el producto puede llegar a él por una vía real —un emisor que existe o que entrega el hito, un argumento, una bandera o una variable de quien usa el kit, o un estado que crea el propio binario, incluidas sus invocaciones concurrentes y la interrupción de sus propias escrituras si el hito promete atomicidad— y si sus lecturas dan un resultado observable distinto para una persona o una skill. El motivo nombra las dos cosas («vía: …; diferencia: …»). Lo que llega de fuera manipulado lo cubre una regla genérica —defecto `inesperado`, código 1 (ADR 0023)— y ningún artefacto lo especifica caso a caso; si ya lo hace, el motivo es retirarlo.
   - **Uso, de fuera adentro** (`juez_spec` criterio i, `juez_plan` criterio m, los dos jueces finales criterio j): cada salida que consume una skill o una persona dice quién la pide y cuántas veces por pregunta, qué tamaño tiene con meses de uso (cientos de normas y miles de bloques) y cuándo deja de darse cada señal, con un cálculo (o, en la revisión final, una medida en el binario) como evidencia. El corrector del plan puede tocar `spec.md` solo para un motivo de uso cuya causa esté en el spec.
   - **Proporcionalidad** (`juez_plan` criterio n, juez B de la revisión final criterio k): la solución más simple que cumple el spec; cada mecanismo se traza a un FR/SC, y lo que no se traza se retira.
   - **Umbrales que se cumplen** (`juez_spec` criterio j, `juez_plan` criterio o, los dos jueces finales criterio l; `juez_tasks` lo cubre en su criterio b): todo requisito o criterio de éxito con un umbral numérico que se mide sin persona —en `make ci` o en el cierre— tiene un control que pone esa comprobación en rojo cuando la medida pasa del umbral. El spec nombra una comprobación que falla; el plan, en la sección `## Controles de umbral` (`| Requisito | Umbral | Control | Dónde |`, con «Dónde» `ci:<ruta>`, `ci:<ruta>:<Test>` o `evals:<skill>:<nombre>`), dice dónde vive y hace que mida cada forma que promete el requisito; cada fila tiene su tarea; y la revisión final comprueba en el código que existe y que falla, con un mutante si hace falta. Publicar la medida no es un control, la regla por serie del ADR 0016 no sustituye a un umbral agregado, hacer cumplir un umbral del hito no es alcance añadido y ningún corrector lo arregla rebajando el umbral o dejándolo solo publicado. El corrector del plan puede tocar `spec.md` por un motivo de umbral cuya causa esté en él. Un umbral que solo mide una persona, o uno del repositorio cuyo control vive en configuración que el hito no toca (la cobertura de `codecov.yml`), no es motivo del hito. Las letras nuevas siguen a la última usada en cada juez, para que los veredictos de runs distintos se comparen por letra.
   - **Convergencia** (todos los gates): desde la segunda ronda un motivo nuevo solo cuenta si lo introdujo la corrección anterior o si es material. Para que el juez lo compruebe, `gate.sh leer` guarda una instantánea de los artefactos juzgados en el git-dir (`kitlegal-gates/<fase>-r<n>/`, fuera del historial) y `gate.sh cambios`, al empezar la ronda siguiente, deja en `gates/<fase>-correccion-r<n>.diff` exactamente lo que cambió el corrector. En la revisión final cada cambio es un commit: `gate.sh leer` apunta en `gates/revision-juzgado.json` la cabeza que juzgó cada ronda, y `preparar_jueces` (`scripts/workflow/revision.sh cambios`) escribe en `gates/revision-cambios.md` el rango desde el último veredicto —cada commit, el paso que lo hizo y sus ficheros— y su diff fuera de `gates/` en `gates/revision-cambios-r<n>.diff`. Todo ese rango es «la corrección», sea del corrector o de una reparación del cierre (ADR 0030).

   Lo que el juez ve y no llega a motivo va a `observaciones`: queda archivado con la ronda, no cuenta para el veredicto y no llega al corrector. El informe final lo cuenta.
3. **Humano, en los extremos.** Antes del run, la sección del hito y la fila revisada de `docs/SOURCES.md` en `main` para toda fuente que se vaya a grabar. Después, el informe final: fuentes, anomalías, adaptadores nuevos, fixtures y esquemas modificados, grabaciones, evidencia y supuestos, antes de fusionar.

## Clarificación sin sesgo y sin persona

`clarify` se divide para que quien formula las preguntas no sea quien las responde:

1. **`clarify_preguntas`** ejecuta `/speckit-clarify` con la orden de solo escribir las preguntas y sus opciones en `gates/clarify-preguntas.json`, sin recomendación ni opción preferida, y sin tocar el spec.
2. **`resolver_clarify`** es un `prompt` en un proceso `claude -p` nuevo que decide solo con documentos (hito, `CLAUDE.md`, `refs/`, constitución): (e) antes que nada, una pregunta que no pasa el umbral de materialidad se responde «no material: lo cubre la regla genérica» y no añade nada al spec; (a) lo determinan las fuentes → esa es la respuesta; (b) no está especificado → «fuera de alcance: no se implementa»; (c) varias opciones válidas → la de mayor calidad, con la alternativa rechazada; (d) alcance, frontera humana, privacidad, TOS, anomalías o decisión cerrada → **lectura conservadora** con `conservadora: true`. Nunca escala. Cada respuesta lleva su `impacto` (`comportamiento`, `alcance`, `skill` o `interno`), que ordena el informe final.
3. **`check_clarify`** comprueba que cada pregunta tiene respuesta; si falta alguna, `resolver_clarify` lo intenta de nuevo (tres veces). **`completar_clarify`** cierra lo que quede sin respuesta como «fuera de alcance». **`clarify_integrar`** lleva los pares Q/A a `spec.md` con marca `(auto: criterio …)` o `(auto: conservadora …)`.

## Implementación tarea a tarea

El bucle toma la primera línea `- [ ] Tnnn` que no está en cuarentena, anota el commit base, las rutas que declara y la huella de su nota, y lanza `/speckit-implement` restringido a esa tarea.

- **Guardián de diff** (`scripts/workflow/guardian-diff.sh tarea`): el diff desde la base se limita a las rutas declaradas, más `go.mod`, `go.sum`, `CHANGELOG.md`, el directorio del feature y `x_test.go` de un `x.go` declarado; declarar un directorio permite todo lo que cuelga de él. `testdata/` y `schemas/` solo con `[datos]`; `evidencias/` nunca (la escribe `grabar_datos`); la suite de aceptación congelada nunca; ningún `t.Skip` nuevo. `.golangci.yml` se admite sin declararlo solo cuando el diff se limita a añadir entradas a `misspell.ignore-rules` (palabras españolas que el diccionario inglés toma por erratas). Una violación es un rojo como otro: el reparador la ve en `gates/ci.log`.
- **Verificación** (`scripts/workflow/verificar.sh tarea`): guardián; «rojo primero» si la tarea es `[aceptacion]`; manifiesto grabable si es `[datos]`; y `make ci` (sin `Makefile`, `go build ./... && go vet ./... && go test -race ./...`). La última línea de `gates/ci.log` es `kitlegal-verificacion exit=N`, que `estado_cierre` lee en lugar de fiarse de salidas de pasos que quizá no se ejecutaron.
- **Rojo**: si la tarea quedó **redelimitada** (sigue `[ ]` y su nota cambió en este intento, normalmente con la línea de `tasks.md` ampliada), no se repara ni se commitea: el intento siguiente relee la línea con sus rutas nuevas y hereda el árbol. En cualquier otro rojo, `reparar` recibe las últimas 80 líneas del log; si sigue en rojo, `registrar_fallo` añade el diagnóstico a `gates/tarea-Tnnn.md` y el intento siguiente (con `modelo_escalada`) parte de ahí.
- **Cuarentena**: una tarea que no queda `[X]` en verde tras tres intentos —o marcada `[X]` sin que dos iteraciones de cierre la dejen commiteada— aparta su trabajo como `gates/cuarentena/Tnnn.patch`, el árbol vuelve al último commit en verde (el directorio del feature conserva su contenido, salvo la suite congelada) y el bucle sigue. Tres cuarentenas seguidas sin ninguna tarea en verde entre medias son una causa mayor: DAG bloqueado.
- **Aceptación congelada**: la primera tarea, `[aceptacion]`, escribe desde el spec los guiones testscript de la entrega en `<feature>/aceptacion/*.txtar` (y las evals de la skill si el hito la toca). `scripts/workflow/aceptacion.sh rojo-primero` copia cada guion un momento a `internal/app/testdata/script/` y exige que falle por una aserción: uno que pasa sin implementación, o que falla por no poder leerse, no prueba nada. Tras el commit, `congelar` guarda las huellas en `gates/aceptacion-congelada.json`; al acabar el bucle, `activar` los copia a `internal/app/testdata/script/<hito>-*.txtar` y desde ahí `make ci` los ejecuta. Si el plan dice «Aceptación e2e: no aplica», no hay tarea `[aceptacion]`.
- **Datos externos**: una tarea `[datos]` deja el manifiesto `<paquete>/testdata/grabaciones.json` (con `fuente`) y su test `//go:build grabacion` `TestGrabar*`. Tras su commit, `grabar_datos` (`scripts/workflow/grabar-datos.sh grabar`) comprueba que la fuente tiene fila en `docs/SOURCES.md` de `main` con «Revisado» fechado, ejecuta el test con `KITLEGAL_RECORD=1` y `KITLEGAL_EVIDENCIAS=evidencias/<hito>`, admite solo lo escrito bajo `testdata/` del paquete y `evidencias/<hito>/`, registra huellas en `gates/grabaciones.md` y `evidencias/<hito>/manifiesto.json` (los ficheros de más de 20 MiB solo con su huella; copia en `~/.local/share/kitlegal/evidencias/<hito>/`) y commitea `chore(<hito>): grabaciones de …`. Los ficheros de `data/` derivados los produce código a partir de lo grabado.
- **Converge**: cuando no queda ninguna tarea pendiente, `converge` compara el código con los artefactos una sola vez y añade a `tasks.md` lo que falte; esas tareas pasan por el mismo bucle.

Para que la verificación por tarea tenga sentido, `tasks` recibe la regla de que cada tarea es una rebanada vertical (test + implementación) que deja `make ci` en verde por sí sola, con todas sus rutas declaradas.

## Del make ci del hito a la revisión

- **`ci`** ejecuta `verificar.sh global` con la suite congelada ya activada. En rojo, `bucle_reparacion` (hasta tres intentos) llama a `reparar_hito` y `cerrar_reparacion`.
- **Pasos globales** (`scripts/workflow/global.sh`): `base` fija el commit de partida y `cerrar` verifica desde él con el guardián global —nadie toca `testdata/`, `schemas/`, `evidencias/`, la configuración de verificación (`.golangci.yml`, `codecov.yml`, `lefthook.yml`, `.github/`, `tools/`, `scripts/workflow/`, `.specify/`, `.claude/`) ni la suite congelada— y `make ci`. En verde, commitea; también una corrección que solo toca artefactos del feature (`spec.md`, `quickstart.md`, `research.md`…), y solo deja sin commitear lo que se limita a `gates/`, que versiona el paso siguiente (en H7.2 una corrección de la revisión así quedó fuera de su commit, ADR 0029). Si el guardián lo rechaza, **aparta** todo lo hecho desde la base como `gates/aparcado-N.patch` y vuelve a ella. Con `make ci` en rojo, commitea marcándolo en el mensaje para que el paso siguiente lo vea, salvo en el barrido, que se aparta. En la revisión final y el cierre, `base` guarda además el mensaje del commit (`gates/base-global-pendiente`) hasta que `cerrar` termina: si el run se interrumpe a mitad del corrector o de la reparación, `retomar` hace al reanudar el `cerrar` que faltaba, y lo que dejó queda commiteado o apartado, nunca suelto ni fuera de la vista de los jueces.
- **Barrido** (`barrido`, `modelo_redaccion`): tras H6, donde la revisión final dio 13 rondas por afirmaciones que el producto ya no sostenía, un paso contrasta de una vez los artefactos del hito y la documentación del repositorio (README, CONTRIBUTING, CHANGELOG, `docs/`, `SKILL.md`, comentarios de paquete, cifras y ejemplos) con el código y el binario, y corrige el texto, nunca el código.

## Revisión final con dos jueces

`preparar_jueces` escribe qué juzga la ronda (`gates/revision-cambios.md`: el hito entero en la primera; en las siguientes, el rango desde el último veredicto con su diff) y genera los dos papeles; `revision_jueces` (paso `fan-out`, `max_concurrency: 2`) lanza la plantilla `revision_juez` una vez por juez, **en paralelo** y sin que ninguno vea el veredicto del otro: el item `a` (`modelo_revisor`) evalúa la Definition of Done con rúbrica; el item `b` (`modelo_adversario`, otra familia de modelo) parte de la hipótesis contraria y busca atajos, fixtures o guiones congelados retocados, datos de `data/` que no salen de lo grabado, tests vacíos, promesas que el binario no cumple y alcance excedido, mutando el código en una copia desechable. Ninguno modifica ficheros ni ejecuta `make ci` en el árbol. `leer_revision` archiva los dos veredictos de la ronda (`gates/revision-{a,b}-r<n>.json`) y la cabeza que juzgaron (`gates/revision-juzgado.json`): ambos aprueban → sigue; cualquier rechazo → `corrector_revision` aplica la **unión** de los motivos, `cerrar_correccion` verifica y commitea, y nueva ronda (hasta cuatro veredictos por ciclo). `cerrar_revision` cierra el ciclo y commitea los veredictos; si las rondas se agotan sin aprobar, los motivos van a `gates/revision-pendiente.md` y al informe, y el run sigue. Si un ciclo posterior aprueba, el pendiente anterior queda como `gates/revision-pendiente-resuelto-r<n>.md`.

**Lo que cambia el cierre vuelve a la revisión (ADR 0030).** Desde el ADR 0029 un umbral del job de evals decide, así que un cierre en rojo es normal y `reparar_cierre` puede cambiar código, tests, la skill, las evals o los artefactos. Por eso la revisión final y el cierre viven en el mismo bucle, `bucle_final`, y la revisión va por **ciclos**: el primero juzga el hito; cada uno de los siguientes, lo que cambió fuera de `gates/` después del último veredicto. Al empezar cada vuelta, `pendiente_revision` (`scripts/workflow/revision.sh pendiente`) lo decide con el estado del disco: continúa un ciclo abierto (una reanudación a mitad de ronda), abre el primero si no hay veredictos, abre uno nuevo si algo cambió fuera de `gates/` desde la cabeza juzgada —commits o cambios sin commitear— y, si no, no juzga nada. Una reparación que solo toca `gates/` no lanza ninguna revisión. Cada ciclo tiene su propio tope (cuatro veredictos, tres correcciones: el de la constitución), las rondas se numeran seguidas en todo el run y el ciclo abierto vive en `gates/revision-ciclo.json`. Los jueces juzgan la reparación con la rúbrica entera: si se aparta de lo que piden la sección del hito, el spec o lo que decidió un hito anterior, solo cumple si es la mejor solución a la vista de la medición y está registrada como decisión, con su evidencia, en `research.md` o `plan.md` y en `gates/supuestos.md`.

La regla «desacuerdo → humano» se retiró con datos de H1 (ADR 0007): el desacuerdo medía la profundidad de cada juez, no la ambigüedad del código; por eso los dos jueces tienen la misma capacidad y la diversidad está en el prompt y en la familia de modelo.

## Cierre en la plataforma e informe final

El cierre va **después** de la revisión, sobre la cabeza que se va a fusionar: en H5 y H6 la ejecución de cierre de las evals era una tarea `[plataforma]` anterior a la revisión, y cada corrección la dejaba sin cubrir la cabeza. Ya no existen las tareas `[plataforma]`.

- **`publicar`** (`scripts/workflow/cierre.sh publicar`) commitea los registros del directorio del feature, empuja la rama y abre la propuesta de cambio hacia `main` si no existe. Corre en cada vuelta de `bucle_final`; tras la primera solo empuja.
- **`medir_cierre`** (`cierre.sh medir <hito> 3`) quita y vuelve a poner la etiqueta `evals` (el botón de «vuelve a medir» de `.github/workflows/evals.yml`), espera a que terminen todas las comprobaciones de GitHub Actions sobre la cabeza (hasta 3 h) y escribe `gates/cierre.json` y, de cada ejecución en rojo, el final de `gh run view --log-failed` en `gates/cierre.log`. De cada trabajo de evals que terminó copia su `informe.json`, que el job imprime entero en su registro entre las marcas `--- inicio de informe.json ---` y `--- fin de informe.json ---`, a `gates/evals/<skill>.json`; `cierre.sh evals <hito>` hace solo esa recogida, sin empujar ni etiquetar, para un run que midió con un workflow anterior. Los estados de Codecov son informativos. Un umbral que el job publica en `umbrales` con `decide: true` pone su veredicto en fallo cuando no se cumple (contrato del ADR 0029), así que el cierre sale en rojo. **Una medición vale solo para el producto que midió** (ADR 0030): `medir` se repite en cada vuelta, salvo que desde la última nada haya cambiado fuera de `gates/` y ninguna reparación haya terminado (`gates/cierre-reparaciones`), que es el caso de una reanudación entre la medición y el final de su reparación; entonces se reutiliza sin gastar otra. Tras una reparación terminada se mide siempre, aunque no cambiara nada: un rojo de la plataforma solo se aclara volviendo a medir.
- **`reparar_cierre`** (`modelo_escalada`) arregla en rojo, nunca rebajando un umbral; `cerrar_cierre` (`cierre.sh reparado`) verifica, commitea y cuenta la reparación. Si cambió algo fuera de `gates/`, la vuelta siguiente lo lleva a un ciclo de la revisión final y **después** vuelve a medir: cada reparación la juzgan los dos jueces antes de que se mida, y lo que corrige esa revisión entra en la misma medición. Tres mediciones y dos reparaciones como mucho; el bucle siempre termina en una medición del producto ya juzgado.
- **`informe_final`** (`scripts/workflow/informe.sh`) escribe sin modelo `gates/informe-final.md`, lo commitea, lo empuja y lo pone de cuerpo de la propuesta, en el orden en que la persona tiene que leerlo (ADR 0028): (1) estado local y remoto, con el veredicto de evals de cada skill; (2) supuestos por impacto: enteros los que cambian el comportamiento visible, el alcance o una skill, después los del propio run (gates agotados con sus motivos pendientes, cuarentena, observaciones de los jueces), después los que no llevan etiqueta —runs anteriores a la 2.1.0, enteros para no esconder ninguno— y los internos solo contados por autor; (3) la tasa de cada eval del job sobre la cabeza, una tabla por skill con una columna por modelo, con las nuevas, las cambiadas y las informativas marcadas, y debajo los recuentos que publica el job (`expresiones_prohibidas_por_modelo`: con alguna, total y porcentaje por modelo) y sus `umbrales` (ADR 0029), con los que no se cumplen, los que solo se publican y los incoherentes marcados; (4) lo que la capa 3 reserva a la persona, con los fixtures y esquemas nuevos o modificados nombrados y la suite de aceptación activada aparte; (5) cuarentena; (6) trazabilidad de cada FR/SC a sus tareas, guiones y control de umbral; (7) cambios posteriores a la revisión: cada commit posterior a lo que juzgó la primera ronda, con la ronda que lo vio y su veredicto y lo que toca fuera de `gates/`, y aparte **«Cambios que ningún juez vio»**, que en un run sano está vacía (ADR 0030); (8) duración del run. En la sección 1, la revisión cuenta sus rondas y ciclos, una línea dice cuántos cambios no vio ningún juez y la medición del cierre dice si es el producto de la cabeza.

  En la trazabilidad, «tareas hechas» solo dice que las tareas que citan el requisito están marcadas. «Comprobado por su control» exige su fila en «Controles de umbral» de `plan.md` y que el control esté: `ci:` con la ruta (y la función o el objetivo) en la cabeza y `make ci` en verde, o `evals:` con el umbral publicado por el job, cumplido, coherente con su medida y haciendo fallar el job; si no, «UMBRAL NO CUMPLIDO» o «CONTROL SIN VERIFICAR». Lo decide el script sin modelo; que un control `ci:` falle de verdad por encima del umbral lo comprueba la revisión final (criterio l). `scripts/workflow/informe.sh <hito> --solo-ver` lo muestra sin tocar nada.

  La etiqueta de impacto la pone quien escribe el supuesto: cada línea de `gates/supuestos.md` empieza por `[comportamiento]` (lo que ve quien usa el binario: salida, códigos, ficheros, argumentos), `[alcance]`, `[skill]` (lo que una skill pide, dice o comprueba) o `[interno]`, y los pasos shell anotan `[proceso]` (`anotar_supuesto` en `scripts/workflow/comun.sh`). Una respuesta de clarify sin `impacto`, de un run anterior, cuenta como alcance si dejó algo fuera (criterio b o conservadora) y si no, sin clasificar.

## Modelo por paso

Cada paso `command` y `prompt` lleva `model: "{{ inputs.modelo_<rol> }}"`. El valor es `<modelo>` o `<modelo>@<esfuerzo>`: alias (`fable`, `opus`, `sonnet`, `haiku`) o nombre completo, y esfuerzo `low`, `medium`, `high`, `xhigh` o `max` (Haiku 4.5 no admite esfuerzo). spec-kit solo sabe pasar `--model`, así que `scripts/hito.sh` exporta `SPECKIT_INTEGRATION_CLAUDE_EXECUTABLE=scripts/claude-modelo.sh`: el wrapper valida el valor con una expresión estricta y lo traduce a `claude … --model <modelo> --effort <esfuerzo>`. **Sin el wrapper, `claude` rechaza los valores con `@`**: lanza siempre con `scripts/hito.sh` o exporta esa variable.

Los roles agrupan pasos por el tipo de trabajo, no por fase:

| Input | Pasos | Por defecto | Razón |
|---|---|---|---|
| `modelo_decision` | `resolver_clarify`, `plan`, `corrector_plan` | `opus@xhigh` | Decisiones cuyos errores se arrastran a todas las tareas; sin persona en medio, la lectura conservadora tiene que ser la buena |
| `modelo_juez` | `juez_spec`, `juez_plan`, `juez_tasks` | `opus@xhigh` | El juez debe ser al menos tan capaz como el autor; el de entrada es el único que puede devolver el hito |
| `modelo_revisor` | `revision_juez` (item `a`) | `opus@xhigh` | Rúbrica DoD casi toda comprobable |
| `modelo_adversario` | `revision_juez` (item `b`) | `fable@xhigh` | Último gate antes del cierre: otra familia que `modelo_revisor` para que los dos votos no fallen a la vez (ADR 0007) |
| `modelo_redaccion` | `specify`, `clarify_preguntas`, `tasks`, `corrector_spec`, `corrector_tasks`, `barrido` | `opus@high` | Artefactos largos con muchas reglas; los correctores y el barrido aplican motivos concretos o contrastan texto con código |
| `modelo_implementacion` | `implementar_tarea` (intento 1), `corrector_revision` | `opus@xhigh` | Código y depuración; `xhigh` es el nivel recomendado para trabajo agéntico de código |
| `modelo_escalada` | `implementar_tarea_escalada` (intentos 2 y 3), `reparar`, `reparar_hito`, `reparar_cierre` | `fable@xhigh` | Solo actúa cuando algo ya falló: no repetir con el mismo modelo lo que acaba de salir mal |
| `modelo_analisis` | `clarify_integrar`, `analyze`, `converge` | `sonnet@high` | Lectura, contraste y transformación de artefactos |

Criterio de coste, medido con `scripts/coste-run.sh` en los runs de H2 (`bfa8c3ac`) y H3 (`94612c4d`), a precio de lista: estos pasos son sobre todo lectura de contexto en caché, y Fable 5.1 lee de caché a mitad de precio que Opus 5, así que con el mismo perfil de tokens un paso en Fable cuesta entre 1,4 y 1,7 veces lo que en Opus, no el doble del precio nominal. Hasta el workflow 1.7.0 Fable (jueces, decisión y escalada) era el 44 % del coste de H3; los jueces en Fable no ahorraron rondas frente a los de Opus de H1, y las escaladas de H2 y H3 no fueron límites de capacidad. Desde 1.8.0 Fable queda donde la estructura lo pide (juez adversarial y escalada). Para revisarlo con datos nuevos: `scripts/coste-run.sh` da el coste por paso y por rol de cada run.

Sobrescritura por run:

```bash
KITLEGAL_MODELO_IMPLEMENTACION=opus@max KITLEGAL_MODELO_ANALISIS=haiku scripts/hito.sh H7
```

Los pasos `shell` no usan modelo. Para fijar un modelo distinto en un solo paso sin tocar los inputs, edita su `model:` en el YAML o usa un overlay (`specify workflow overlay add …`).

## Uso

```bash
scripts/hito.sh H7                     # lanza el hito y lo lleva hasta el informe final
scripts/hito.sh --resume <run_id>      # tras resolver una causa mayor (el dossier dice qué hace falta)
scripts/hito.sh --clasificar <run_id>  # qué haría el supervisor con ese run
KITLEGAL_MODELO_FALLBACK=fable=opus,opus=sonnet KITLEGAL_TIEMPO_MAXIMO=259200 scripts/hito.sh H7
scripts/workflow/informe.sh H7 --solo-ver   # el informe tal como está ahora, sin tocar nada
scripts/workflow/cierre.sh evals H7    # recoge las tasas de evals de la última medición (runs anteriores a la 2.1.0)
scripts/paso.sh juez_plan H7           # relanzar a mano un paso prompt (con el run parado)
scripts/paso.sh revision_juez_b H7     # un juez del fan-out de la revisión final (items a y b), con el rango de gates/revision-cambios.md
scripts/workflow/revision.sh cambios H7   # qué juzgaría ahora la ronda siguiente de la revisión final
scripts/coste-run.sh [run_id]          # coste por paso y por rol (por defecto, el run más reciente)
specify workflow status [<run_id>]     # runs y estado
```

Estado de cada run en `.specify/workflows/runs/<run_id>/` (`state.json`, `inputs.json`, `log.jsonl`).

## Supervisor

`specify workflow run` termina en cuanto un paso falla, y el motor no reintenta nada. `scripts/hito.sh` envuelve `run`/`resume` en un bucle que clasifica cada parada leyendo `state.json`, `log.jsonl` y el transcript de la sesión headless (`~/.claude/projects/<ruta>/`), y actúa con una lista cerrada de acciones:

| Clase | Cómo se reconoce | Acción |
|---|---|---|
| `completado` | `status: completed` | Termina y avisa: el informe es el cuerpo de la propuesta |
| `rechazo` | Falla `check_gate_spec` | Se detiene: informe de rechazo en `gates/informe-rechazo.md` |
| `causa_mayor` | Un paso shell sale con 3 | Se detiene: dossier en `gates/dossier.md` |
| `limite` | Paso `prompt`/`command` fallido y la sesión headless posterior a su inicio terminó con `rate_limit`, «spend limit», «usage limit», `overloaded`, `api_error` o «API Error: NNN» | Cambia de familia de modelo (`KITLEGAL_MODELO_FALLBACK`, por defecto `fable=opus,opus=sonnet`, conservando el esfuerzo) en todos los roles que usaban la familia que falló, espera `KITLEGAL_ESPERA_LIMITE` s (60) y reanuda; sin repuesto, espera `KITLEGAL_ESPERA_SIN_REPUESTO` s (1800) y reanuda con los mismos modelos. No consume reanudaciones |
| `transitorio` | Cualquier otro fallo de un paso | Reanuda; el mismo paso no se reanuda más de dos veces, y hay un tope de `KITLEGAL_MAX_REANUDACIONES` (8) por invocación |

Antes de cada reanudación comprueba el presupuesto de tiempo (`KITLEGAL_TIEMPO_MAXIMO`, 48 h desde el primer paso del run). Al arrancar, y al reanudar, comprueba `claude`, la sesión de `gh` y el acceso a `origin`; que ninguna credencial de Claude va en el entorno, que el token del sondeo no está en un fichero, que ningún `settings.json` que lean las sesiones declara directorios adicionales, que el sandbox está disponible y que la política de las sesiones pasa su tabla de casos (ADR 0032); y toma el candado de sesión única. La sesión interactiva que lanza el run puede seguir teniendo sus directorios adicionales en `.claude/settings.local.json` (el registro de `nohup scripts/hito.sh`, por ejemplo): las sesiones del run no leen ese fichero. Mientras vive, mantiene un `caffeinate -i` ligado a su PID: en H3 el Mac se durmió a mitad de `plan` y el hito tardó casi dos horas más. El supervisor nunca edita artefactos, veredictos, `tasks.md` ni permisos: solo relanza `specify workflow resume`. En macOS avisa con una notificación de escritorio al terminar o detenerse.

## Una sola sesión por run

En H6 una copia duplicada de la conversación estuvo trabajando en paralelo sobre el mismo árbol que el run. `scripts/hito.sh` toma un candado en el git-dir del árbol de trabajo (`kitlegal-run.lock`, uno por worktree) con su PID y un testigo aleatorio, y exporta el testigo en `KITLEGAL_RUN_TESTIGO`: lo heredan `specify`, los pasos shell y las sesiones `claude -p` del run. El gancho `PreToolUse` de `.claude/settings.json` (`scripts/workflow/sesion-unica.sh gancho`) rechaza, en cualquier sesión sin ese testigo, `Edit`, `Write`, `MultiEdit`, `NotebookEdit` y las órdenes de `Bash` que cambian el árbol o el historial (`git add|commit|checkout|reset|push…`, `rm`, `mv`, `sed -i`, `scripts/hito.sh`, `scripts/paso.sh`…); leer y `scripts/hito.sh --clasificar` siguen permitidos. `scripts/paso.sh` se niega a correr con un run vivo. Un candado cuyo PID ya no existe se ignora y se recupera.

## Lo que una sesión de un paso no puede hacer

En el run de H7.4 (`0f3ef83d`) las dos invocaciones de `reparar_cierre` leyeron de un fichero el token de la suscripción de quien lanzó el run y abrieron con él, en segundo plano, 42 sesiones con modelo del sondeo local (33 y 9) que nadie había pedido; la segunda cerró sin esperar y citó en `research.md` una verificación que no llegó a producirse. En la segunda, los permisos de Claude Code denegaron seis formas de la orden y pasó la séptima: `rtk proxy sh <guion>`, que casa con `Bash(rtk:*)`, con `run_in_background`; en la primera, `rtk proxy sh -c '…'` a la tercera.

Los permisos no pueden dar esa garantía, y un gancho que mire el texto de la orden tampoco (medido; ADR 0032): una regla `deny` de `Read` solo cubre la herramienta `Read`, y un `cat` —suelto o dentro de un guion— lee el fichero igual; `Read` y `Write` sin ruta valen para cualquier fichero del equipo; y `Bash(rtk:*)`, `Bash(make:*)` y `Bash(go:*)` ejecutan cualquier programa, porque el run tiene que compilar y probar código. Lo que no hace el texto lo hace el sistema operativo, y lo que no puede el sistema operativo, el sitio donde vive el secreto:

| Qué | Qué lo impide | Dónde |
|---|---|---|
| Usar la credencial del sondeo | No está en ningún fichero. En macOS vive en un llavero propio y bloqueado: leerlo abre el diálogo del sistema, que pide su contraseña a la persona, y el guion lo vuelve a bloquear en cuanto tiene el valor. `hito.sh` no arranca si el fichero antiguo existe o si `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY` o `ANTHROPIC_AUTH_TOKEN` están en el entorno | `scripts/evals-sondeo-llavero.sh`, `scripts/hito.sh` (`comprobar_entorno`) |
| Leer otros secretos | El sandbox de Claude Code (Seatbelt en macOS, bubblewrap en Linux) niega a toda orden de `Bash`, y a todo lo que esa orden ejecute, la lectura de `~/.config/kitlegal`, `~/.config/gh`, `~/.ssh` y los directorios de `KITLEGAL_SECRETOS`; las mismas rutas van denegadas a la herramienta `Read` | `scripts/claude-modelo.sh` |
| Abrir sesiones con modelo, empujar, usar `gh` o tocar una fuente | El sandbox solo deja salir a `proxy.golang.org`, `sum.golang.org` y `vuln.go.dev`, que usan las herramientas de Go, y al propio equipo, que usan los tests: sin `api.anthropic.com` un `claude` no abre sesión se lance como se lance, también por su ruta absoluta desde un guion. Además, el `claude` del `PATH` es un sustituto que termina con 1 y dice por qué, y `make evals-sondeo` se niega a correr dentro de un paso o con un run vivo | `scripts/claude-modelo.sh`, `scripts/workflow/sin-modelo/claude`, `scripts/evals-sondeo-llavero.sh` |
| Escribir fuera de lo declarado | El sandbox solo deja escribir en el repositorio, en el directorio temporal (`$TMPDIR`, que el sandbox pone a la sesión, y el del usuario en macOS; `/tmp` no) y en las cachés de Go y de golangci-lint. `Write`, `Edit`, `MultiEdit` y `NotebookEdit` no pasan por el sandbox: el gancho solo los admite en el repositorio, el directorio temporal y la memoria del proyecto. Las sesiones no leen `.claude/settings.local.json` (`--setting-sources user,project`), así que los directorios adicionales de la sesión interactiva de quien lanza el run no les llegan, y `hito.sh` no arranca si el `settings.json` del proyecto o el de la cuenta declaran `permissions.additionalDirectories`, que el sandbox abriría a la escritura | `scripts/claude-modelo.sh`, `scripts/workflow/politica-paso.sh`, `scripts/hito.sh` |
| Dejar algo en segundo plano | Claude Code no ofrece `run_in_background` ni pasa una orden al fondo cuando vence su plazo (`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`); el gancho deniega además `nohup`, `disown`, `setsid` y `&` en el texto de la orden | `scripts/claude-modelo.sh`, `scripts/workflow/politica-paso.sh` |

Todo se aplica en `scripts/claude-modelo.sh`, la única puerta por la que el workflow y `scripts/paso.sh` abren una sesión. El sandbox va con `failIfUnavailable` (la sesión no arranca sin él; `hito.sh` lo comprueba antes), sin la salida `dangerouslyDisableSandbox` (`allowUnsandboxedCommands: false`) y sin aprobar por sí mismo ninguna orden (`autoAllowBashIfSandboxed: false`: los permisos de `.claude/settings.json` deciden lo mismo que antes). Si quien llama trae su propio `--settings`, el wrapper le pone encima los del paso, porque Claude Code solo atiende uno. `enableWeakerNetworkIsolation` deja a Go comprobar los certificados con el servicio del sistema; sin él `govulncheck` no llega a `vuln.go.dev`. El wrapper exporta `KITLEGAL_PASO_DE_WORKFLOW`, y con esa marca el gancho `PreToolUse` de siempre (`sesion-unica.sh gancho`) entrega cada llamada a `politica-paso.sh`, sin tocar `.claude/settings.json`. Una sesión interactiva no pasa por el wrapper y no cambia. `hito.sh` ejecuta al arrancar `scripts/workflow/politica-paso.sh prueba`, la tabla de casos del gancho, con las órdenes del incidente dentro.

El gancho mira el texto de la orden y no ve lo que hace un guion o un programa que la sesión escriba y ejecute: de él depende lo que no pasa por el sandbox (`Write` y `Edit`), y en lo demás da el motivo antes y en la propia sesión. Repetidas por él las 2 110 llamadas `Bash`, `Write` y `Edit` de las 41 sesiones del run de H7.4, deniega 56 —las del incidente, tres `claude --version`, las órdenes que los jueces dejaron en segundo plano y las copias que el juez B editó en `~/Library/Logs/kitlegal`— y ninguna otra.

**Lo que queda.** Un proceso que un guion deja atrás con `&` sobrevive a la sesión: el segundo plano dentro de un guion no lo ve el gancho ni lo impide el sandbox. Sigue dentro del sandbox —sin red, sin secretos y sin escribir fuera del repositorio y del temporal—, así que no puede abrir sesiones con modelo ni usar una credencial; lo que puede es seguir trabajando en el árbol cuando el paso ya ha terminado. Contra eso están la regla del prompt, el motivo de cada denegación, la verificación del workflow (que mide el árbol después del paso) y los jueces. Y en macOS el diálogo del llavero aparece si una sesión lo pide desde un guion: la persona no escribe la contraseña de un diálogo que no ha provocado.

**Lo que cambia para un paso.** `make ci` entero pasa dentro del sandbox (medido en un clon, unos 3 minutos). Las copias de los jueces y los binarios de prueba van a `$TMPDIR`, no a `/tmp`. `git fetch` y `git ls-remote` fallan —el script de spec-kit que crea la rama del hito lo tolera y numera con lo que hay en local—, y `.git/config` no se puede escribir. Una orden que no termina en el plazo de la herramienta (600 s como mucho) se corta en lugar de pasar al fondo.

Lo mismo lo dice el prompt de los 22 pasos con modelo (13 `prompt` y 9 `command`), con una línea igual en todos, «SESIÓN DE UN PASO»: primer plano, sin sesiones con modelo ni credenciales, el sandbox, y ninguna evidencia que no se haya producido. `reparar_cierre` diagnostica una eval en rojo con lo que el job dejó en `gates/evals/<skill>.json`, sin repetir sesiones: lo que cambia lo mide el job en la medición siguiente. Los jueces de la revisión final ya tratan como motivo la cita de una verificación que no está en el repositorio (criterio f, y «con su evidencia» en los cambios del cierre): los dos la cazaron en el ciclo 3 de H7.4, así que la rúbrica no cambia.

El sondeo sigue siendo de la persona: `make evals-sondeo …` en una sesión interactiva, a petición suya, abre el diálogo del llavero y ella escribe la contraseña (`CONTRIBUTING.md`, «Sondeo local»).

## Permisos de Claude en modo headless

`claude -p` respeta `.claude/settings.json`. Para que `implement` pueda compilar y testear sin prompts el proyecto necesita una lista de permisos como la del fichero (`deny` gana a `allow`; como `Bash(git:*)` ya permite `git push`, la política se expresa en `deny`: `main`, push forzados, borrados, etiquetas y el `git push` sin argumentos quedan denegados; la garantía real la da `scripts/lefthook/pre-push/guardia-push.sh`, que ve las referencias que git va a enviar). Desde la 2.0.0 publicar y medir en la plataforma lo hacen los pasos shell `publicar`, `medir_cierre` e `informe_final`, que no pasan por los permisos de Claude, y los prompts de los pasos con modelo prohíben `git push` y `gh`. Los permisos siguen admitiendo `git push` de ramas y `gh pr create|edit|view|checks` porque los usan las sesiones interactivas; lo que nunca admite ninguna sesión (fusionar, empujar a `main`, forzar, borrar, etiquetar) lo sigue garantizando el gancho `pre-push`.

`scripts/hito.sh` exporta `SPECKIT_INTEGRATION_CLAUDE_EXTRA_ARGS="--permission-mode acceptEdits"`. En un entorno aislado (contenedor o VM) puede sustituirse por `--dangerously-skip-permissions`.

Los permisos no son la garantía de lo que una sesión del run no puede hacer: esa garantía está en la sección anterior.

## Limitaciones conocidas

- Las sesiones de un paso corren en el sandbox de Claude Code (ADR 0032), que en macOS es Seatbelt y en Linux necesita `bwrap` y `socat`; sin él no arrancan. No tienen segundo plano: una orden que no termina en el plazo de la herramienta (600 s como mucho) se corta. `make ci` cabe; lo que no quepa se parte.
- Los pasos `command` transmiten la salida al terminal y no la capturan; por eso los jueces escriben ficheros en `gates/` y `analyze` recibe la instrucción de guardar su informe.
- Los pasos `shell` tienen `timeout` explícito (1800 s los que ejecutan `make ci`, 3600 s `grabar_datos`, 11 400 s `medir_cierre`); los pasos `prompt`, 3600 s; `pendiente_revision`, 1800 s, porque puede cerrar un paso interrumpido con `make ci`. Un corte dentro de una ronda lo trata el supervisor como transitorio, y `resume` repite la ronda entera.
- **`resume` reejecuta el paso de nivel superior**, no el paso anidado que falló (`engine.py`: «resume will re-run the parent step and its nested body»). En `bucle_final` significa volver a entrar por `pendiente_revision`: cierra con su propia verificación el paso con modelo que quedó a medias (`global.sh retomar`, con el mensaje que guardó `global.sh base`), continúa el ciclo de revisión abierto con las rondas que le quedan, no repite una revisión aprobada sin cambios y reutiliza la medición si sigue valiendo; las mediciones y reparaciones cuentan en ficheros. El motor anida bucles (un `do-while` dentro de un `if` dentro de otro `do-while`, como `ronda_revision` en `bucle_final`), pero no guarda la posición dentro de ellos: por eso todo lo que decide el bucle está en el disco. Dentro de `bucle_tareas` significa una **iteración nueva**: `siguiente_tarea` detecta una tarea marcada `[X]` con cambios sin commitear y emite una iteración de **cierre** (sin implementar: verificación y commit con la base original). Las rondas cuentan en `gates/<fase>-rondas`, que solo pone a cero el paso `iniciar_*` anterior al bucle; tras un `resume` con las rondas agotadas, el bucle ejecuta un solo juez y `cerrar` decide.
- **El motor conserva la última salida de cada id de paso entre iteraciones del bucle**, y una condición que lea la de un paso que no se ejecutó en esta iteración lee la de la anterior (H4, T003: 145 vueltas). Regla para el YAML: una condición solo puede leer salidas de pasos que se ejecutan incondicionalmente en la misma iteración; `estado_cierre` decide el commit con la última línea de `gates/ci.log` y con `tasks.md`.
- **Cada run congela el workflow**: `specify workflow run` copia la definición a `.specify/workflows/runs/<run_id>/workflow.yml` y `resume` la lee de ahí. Los scripts de `scripts/workflow/` no se congelan: un cambio en ellos afecta a los runs en curso.
- El guardián extrae rutas de la línea de la tarea: tokens con `/`, con extensión conocida, ficheros de raíz sin extensión que terminan en `ignore`, `.editorconfig`, `Makefile` y `LICENSE`. Una tarea que toque muchos ficheros debe declarar directorios.
- El supervisor reconoce el límite de uso por el texto del transcript; un error nuevo con otra redacción se clasifica como `transitorio`. Las sesiones headless se reconocen por el entrypoint `sdk-cli`, que fija `scripts/claude-modelo.sh` (para runs anteriores a esa corrección: `KITLEGAL_ENTRYPOINTS_HEADLESS=sdk-cli,claude-vscode`).
- La batería por tarea ejecuta `make ci` completo tras cada tarea; en hitos grandes es lento pero determinista.
- `inputs.hito` se interpola en pasos `shell`; está restringido por `enum`. No añadir inputs libres a pasos `shell`.
- Si `speckit init` se actualiza (`specify integration upgrade`), regenera `.claude/skills/speckit-*`; el workflow, `scripts/workflow/` y la constitución no se tocan.
